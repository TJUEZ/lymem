# lymem（麟忆尽智）技术文档

面向银河麒麟桌面操作系统 V11 的 OS Agent 记忆系统。Rust 实现，端侧部署，
存储与检索全部走系统自带的向量数据库 SDK，无云依赖。

本文档覆盖：软件架构、算法原理、实现方案、安装部署、效果验证报告（测试数据集
说明、对比实验设计、量化评测实施、指标分析）。操作说明另见《用户手册》。

## 一、设计目标与约束

赛题的硬性约束决定了三个设计决定：

1. 必须部署在银河麒麟 V11，向量检索必须用系统向量数据库 SDK。所以存储层做成
   可切换后端：竞赛正式跑 `kylin`（麒麟向量引擎），开发降级跑 `sqlite-vec`。
2. 端侧意味着资源有限。检索全程本地（嵌入走麒麟 SDK，检索走引擎），只有偏好
   抽取慢通道和蒸馏这种离线动作可以选配外部 LLM，且未配置密钥时自动降级为
   规则兜底——系统在任何配置下都能跑，只是聪明程度不同。
3. OS Agent 的记忆来源杂：工具输出、用户行为、手动配置、对话内容。所以入口
   做成统一事件流，清洗之后再进管线。

## 二、总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                接入层（lymem-server / lymem-cli）             │
│   REST API · /v1/embeddings 代理 · Web 管理界面（viewer）     │
├─────────────────────────────────────────────────────────────┤
│                      lymem-core 记忆核心                     │
│  四层记忆体系          管道                     检索          │
│  ┌──────────┐   多源接入 ingest     三路混合检索             │
│  │ 工作记忆  │──flush──┐ (清洗/去重/    ├ 向量 ANN(麒麟引擎) │
│  │ (短期)    │         ▼  敏感分级)    ├ BM25(tantivy)     │
│  │ 情景记忆  │──consolidate──┐        └ 图扩展(实体/边)    │
│  │ (中期)    │               ▼        └── RRF 融合→偏好重排 │
│  │ 知识记忆  │◄──── 蒸馏 ──┘  冲突管道                       │
│  │ (长期)    │       (检测→分类→仲裁→版本化)                 │
│  │ 偏好记忆  │   偏好双通道(规则+LLM) + 版本时间线            │
│  └──────────┘   遗忘(软删/硬清除) + 审计                      │
├─────────────────────────────────────────────────────────────┤
│  lymem-kylin 麒麟端侧绑定        lymem-llm (OpenAI 兼容)     │
│  DBus SDK 通道 + kytensor 直连   MiniMax 预设,未配置规则兜底  │
├─────────────────────────────────────────────────────────────┤
│  SQLite(元数据/审计) + 麒麟向量引擎 SDK(主) + tantivy(FTS)   │
└─────────────────────────────────────────────────────────────┘
```

四层记忆对应赛题的短/中/长期划分：工作记忆是当前任务的临时上下文；情景记忆按
场景留存过程记录；知识记忆是蒸馏后的可复用知识；偏好记忆独立成层，因为它有
自己的版本化要求。层间流转由 `promotion` 管道驱动：工作记忆按窗口 flush 到
情景记忆，情景记忆按访问频次和时效晋升为知识记忆。

代码分六个 crate：`lymem-core`（记忆核心）、`lymem-server`（HTTP 服务）、
`lymem-kylin`（麒麟绑定）、`lymem-llm`（LLM 网关）、`lymem-cli`、`lymem-bench`
（评测）。核心无外部服务依赖，单二进制可跑。

## 三、关键算法原理

### 3.1 多源接入与清洗（ingest）

所有记忆以事件进入（`type` + `data`：tool_result / user_action / config /
conversation）。管线依次做：空白规范化与长度截断 → 去重指纹（同内容短窗内不
重复入库）→ 敏感识别分级 → 实体抽取 → 入库。多源汇聚（hub）支持从其他 agent
的终端记忆文件发现、解析、清洗后导入，导入映射表（hub_imports）保证重导幂等。

### 3.2 敏感信息分级（sensitive）

入库前对内容做规则扫描，命中敏感模式（证件号、手机号、密钥样式等）的记忆被
分级标记。高级别记忆默认不进入检索结果，遗忘指令支持按敏感级别批量清除。这一步
在入库管道里做而不是查询时做，目的是让敏感内容从一开始就不落检索索引。

### 3.3 三路混合检索与 RRF 融合（retrieval）

同一查询走三路：向量 ANN（麒麟引擎）、BM25 关键词（tantivy）、图扩展（实体
相邻记忆）。三路结果用 Reciprocal Rank Fusion 融合，再按用户偏好重排。
三路各自可开关（`use_graph` 等参数），这套消融开关也是评测工具的一部分——
七站和 LoCoMo 的对照实验就是靠它做通道消融的。

为什么三路而不是纯向量：七站语料里有大量精确实体（预订号、站名、工具参数），
纯向量对这类查询不稳定；BM25 补精确匹配，图扩展补"问 A 得 B"的邻接关系。
消融数据见效果验证报告第五节。

### 3.4 冲突管道（conflict）

四步：检测（新记忆与存量高相似但值不同）→ 分类（时间演化型/矛盾型/补充型）→
仲裁（时间戳优先、来源置信度、显式用户指令最高）→ 版本化（旧值进版本链，不删）。
查询时默认只出仲裁后的现值，版本链可回溯（"用户 5 月的偏好是什么"这类时点查询
直接打版本时间线）。

### 3.5 偏好双通道（preference）

规则快通道正则抓显式表述，毫秒级入库；LLM 慢通道批量扫描对话抓隐式偏好，
结果同样进版本链。跨场景适配指：偏好按场景标记（office / dev / life），
检索时优先同场景偏好，缺位时回退全局。

### 3.6 蒸馏与晋升（consolidate / promotion）

情景记忆按访问频次、复现模式、时效做评分，高分的被蒸馏成知识记忆（含经验卡：
做法、适用条件、踩坑点）。这个过程可以由 LLM 辅助摘要，也可以纯规则聚合。

### 3.7 遗忘（forget）

自然语言遗忘指令（"忘掉关于 doc_edit 的一切"），先解析出目标集合预览，确认后
执行。软删走墓碑（可恢复、审计留痕），硬清除连向量索引一起删。支持按敏感级别
批量清除。

### 3.8 检索兜底与降级

LLM 未配置时：偏好走规则、蒸馏走规则聚合、查询扩展关闭，检索与冲突管线不受
影响。麒麟 SDK 不可用时向量后端可切 sqlite-vec 开发模式。任何一层失效都不
阻断记忆主流程。

## 四、实现方案与部署

### 4.1 构建

```bash
# 银河麒麟 V11（默认编入官方向量数据库 SDK 通道）
cargo build --release
```

产物：`target/release/lymem`（CLI）、`target/release/lymem-server`（HTTP 服务，
内嵌 Web 管理界面）。

### 4.2 部署形态

用户级部署：数据落在 `~/.local/share/lymem`（SQLite 单文件 + 引擎侧向量库），
不写系统目录，不依赖 root。deb 打包脚本在仓库 `packaging/`。首次启动检查
（SDK 合规验收、runtime socket 探测）内置在 `lymem status` 命令里。

### 4.3 服务启动

```bash
LYMEM_PORT=8801 ./target/release/lymem-server
# 浏览器打开 http://127.0.0.1:8801/viewer — Web 管理界面
```

REST API 全集在 `/api/v1/*`：memories（接入）、search（检索）、preferences、
conflicts、forget、consolidate、hub（多源）、audit（审计）、radar（文件雷达）等。
`/v1/embeddings` 提供 OpenAI 兼容嵌入代理（麒麟 SDK 转发），OS Agent 主程序可以
把嵌入基址直接指向本服务。

### 4.4 运维

引擎守护进程由 supervisor 脚本托管（socket 消失自动拉起）；数据备份即拷贝
数据目录；故障排查命令与常见问题见 `docs/部署指南.md`。

## 五、效果验证报告

### 5.1 测试环境

银河麒麟桌面操作系统 V11，x86_64。向量检索：麒麟向量数据库 SDK（unix socket
连本机引擎）。嵌入：系统 Embedding 接口（gte-base，768 维，uint8 量化）。
生成/判分模型：MiniMax-M3 与 deepseek-v4-flash（仅评测环节使用）。

### 5.2 测试数据集说明

| 数据集 | 规模 | 来源 | 对应指标 |
|---|---|---|---|
| 七站（MultiWOZ/ToolBench/PersonaChat/BPMN/DailyDialog/TREC/MS MARCO） | 442/449 查询 | 赛题 PPT 推荐公开集 | 检索召回、延迟 |
| 三国 120 回 | 120 回全文 | 自建（公有领域） | 中文长文档检索 |
| LoCoMo | conv-26 199 问（检索）/100 题（答案）/1986 问（延迟） | 公开 | 检索、端到端 |
| PrefEval | 100 题 | 公开 | 偏好 |
| MemBench | 100 题 | 公开 | 记忆能力 |
| LongMemEval | 100 题 | 公开 | 长程跨会话 |
| MAB-conflict | 100 题 | 公开 | 冲突整合 |
| 自建冲突用例 | 30 组 | 自建 | 冲突回归 |

每个数据集测什么、协议细节、逐题明细位置，见《测试数据集与指标对照》文档。

### 5.3 对比实验设计

- 对照系统：mem0（开源长时记忆框架），同一麒麟嵌入、同一麒麟向量引擎、同一
  生成与判分模型、同一查询集——只对比记忆系统本身的差异。
- 两种对照口径：知识检索口径用"直插向量基线"（文档→向量→top-5，mem0 式 RAG
  上限）；记忆管理口径用 mem0 完整管线（LLM 抽取+原子事实存储）。
- 消融实验：检索三路通道开关（向量/BM25/图扩展），在七站与 LoCoMo 上分别测
  通道贡献。
- 判分协议：客观题用字母匹配（空答算错），开放题用严格 EM 与 LLM 语义判分双口径
  （判分词固定、温度 0），防止单一口径偏差。

### 5.4 量化评测实施方案

每个基准一个驱动脚本，全部可重跑：`ppt_bench.py`（七站）、`run_matrix.py`
（四站矩阵，含断点续跑）、`run_mem0_locomo.py`、`rejudge_longmemeval.py`、
`ppt_bench_mem0.py`。跑批具备：断点续跑（逐题落盘，重启跳过已完成）、限流感知
（限流错误长退避而非判死）、引擎守护自愈。评测产物为逐题 jsonl，汇总数字由
脚本从明细聚合，不存在手抄数字。

### 5.5 量化指标分析

| 指标 | 赛题线 | lymem | 对照（mem0） | 分析 |
|---|---|---|---|---|
| 知识检索召回 | ≥85% | **95.1%**（七站）、41.7%（LoCoMo conv-26 hit@5） | 96.8% / 35.68% | 七站与最强 RAG 基线同水位（天花板在共享嵌入）；超长对话检索 lymem 领先 6 分，来自 BM25+窗口的混合索引 |
| 检索延迟 | ≤500ms | **p50 24~88ms** | p50 ~230ms | 端侧直连，余量一个数量级 |
| 冲突处理 | ≥88% | **93.3%**（受控 30 组）；MAB 22% vs 2% | 2% | 版本链+仲裁的结构性优势 |
| 偏好提取 | ≥85% | **99.0%** | 99.0% | 双通道+版本时间线，接近满分 |
| 记忆能力 | ≥85% | **91.0%** | 88.0% | 知识更新与比较题为主要得分点 |
| 长程跨会话（加测） | — | 54.3%（修复后） | 64.9% | 唯一落后项：多会话聚合题型上区块粒度吃亏，已归因并列入改进（时间推理单项 70% 已反超） |

消融要点（七站）：去掉 BM25，精确实体类查询（预订号、站名）明显掉分；去掉图
扩展，多跳邻接类查询掉分；去掉偏好重排不影响召回率但影响个性化排序。逐通道
数字可在评测工具里用开关复现。

失败案例分析：LoCoMo 检索未命中的题目集中在"跨数百轮的单事实"；LongMemEval
多会话聚合的失败集中在"答案两侧证据只召回了一侧"。这两类都指向同一个改进方向：
更细粒度的记忆单元，已列入路线图。

### 5.6 结论

五项赛题指标全部达标且有数量级不等的余量。与 mem0 的同后端对照，六个对照位
四胜一平一负；唯一负项已完成归因与一轮针对性修复（判分 45.7%→54.3%），剩余
差距是清晰的架构粒度问题，不是能力缺陷。系统的端侧属性（全本地、低延迟、可
降级）与记忆管理能力（冲突、偏好、版本、遗忘）构成了对赛题需求的完整覆盖。
